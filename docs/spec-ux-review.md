# 仕様書: UI/UXレビューと改善提案

- 作成日: 2026-08-19
- 対象: モバイル/PC表示の差異確認、およびUX・UI・コード処理の改善点の洗い出し
- 進め方: 本番環境([https://poker-ledger-alpha.vercel.app](https://poker-ledger-alpha.vercel.app))に対してPlaywrightで実ブラウザ操作を行い、iPhone 13相当(390×664)とデスクトップ(1440×900)の両方で主要画面をスクリーンショット比較。あわせてソースコードを再監査し、処理面の不具合・改善点を洗い出した。合格ラインに達するまで自己レビューを繰り返し、下記に確証のある指摘のみを残した。

## 1. モバイル/PC UIの差異・不具合(要修正)

### 1.1 【重大】テーブルの名前列がモバイルで1文字ずつ縦に折り返される

**再現箇所**: 友達一覧(`/friends`)、対局詳細の収支テーブル(`/sessions/[id]`)

**症状**: `<table>`が`table-layout: auto`のまま複数の数値列(通算収支・勝率・平均収支・参加数など)と組み合わさっているため、モバイル幅(390px)では名前列の確保幅が極端に狭くなり、日本語の名前が「Q/A/テ/ス/ト/A」のように1文字ずつ改行して縦に伸びる。対局詳細ページでは特に列数が多く(参加者・開始時の持ち金額・総バイイン・最後の持ち金額・収支の5列)、名前列の崩れに加えてテーブル自体が画面右端で見切れる。

**原因**: `globals.css`の`table { table-layout: auto }`(既定値)により、ブラウザが各列の内容量から幅を自動配分する際、名前列より数値列の可読性(`white-space: nowrap`は数値セルのみに付与済み)が優先されてしまう。名前セルには`white-space`指定がない。

**デスクトップでは発生しない**(640px幅の余裕があるため)。PCで一度も気づけない典型的なモバイル専用バグ。

**対応案**:
- 名前セルに`white-space: nowrap; overflow: hidden; text-overflow: ellipsis; max-width: <適切な値>`を付与し、長い名前は省略表示にする(最短で確実な修正)
- あわせて`.table-scroll table`に`table-layout: fixed`を検討し、列幅の暴走を防ぐ

### 1.2 【重大】対局詳細ページの収支テーブルがモバイルで横に見切れる

**再現箇所**: `/sessions/[id]` の「収支」テーブル(モバイルのみ)

**症状**: 5列のテーブルが`.table-scroll`(`overflow-x: auto`)でラップされているため技術的には横スクロール可能だが、初期表示の時点で右端の「収支」列が画面端でスパッと切れており、**スクロールできることを示す視覚的なヒント(影・グラデーション・矢印など)が一切ない**。ユーザーは横スクロールに気づけない可能性が高い。

**対応案**:
- `.table-scroll`の右端に薄いグラデーション影を付け、スクロール可能であることを示す(`::after`疑似要素 + `position:sticky`など)
- または対局詳細のテーブルだけ、モバイル幅ではカード型の縦積みレイアウト(リバイ一覧と同じ`.rebuy-item`的なパターン)に切り替える方が、読みやすさの面でも横スクロールより優れる

### 1.3 その他はモバイル/PCで整合していた

ログイン・新規登録・ホーム・ナビドロワー・友達(空/入力済み)・対局記録フォーム・個人成績(統計カード・連勝連敗バッジ・収支推移・カレンダー)・友達追加(QRディープリンク)・友達解除確認は、いずれもモバイル/デスクトップで表示崩れなく一致していた。カレンダーの2列/4列グリッド切り替え(`@media (min-width:480px)`)も正しく機能している。

## 2. コード処理の不具合(要修正)

### 2.1 【バグ】参加者0人でも「確定できます」と表示されてしまう

**場所**: `src/lib/ledger.ts` の `checkZeroSum()`

**症状**: 対局記録画面で参加者を1人も選んでいない状態(`entries = []`)でも、`checkZeroSum`が`{status: "ready"}`を返してしまう。理由は「`cashOut`未入力の参加者がいない」(0人なので当然)ことと「収支合計が0」(空配列の合計は0)を両方満たしてしまうため。結果として、**参加者を1人も選んでいないのに「収支の合計が0円です。確定できます。」という緑のバナーが表示され、確定ボタンが押せる状態になる**(実際に押すとサーバー側のZodバリデーション`entries.min(1, "参加者を選んでください")`で弾かれるため実害はないが、UIとしては明確な誤り)。

**確認画面**: `07-session-new-withfriend__mobile.png`(0/10人選択中の状態で緑バナーが出ている)

**対応案**:
```ts
export function checkZeroSum(entries: EntryInput[], rebuys: RebuyInput[]): ZeroSumCheck {
  if (entries.length === 0) {
    return { status: "incomplete", missingUserIds: [] };
  }
  // ...既存のロジック
}
```
`SessionRecorder.tsx`側の「参加者を選んでください。」メッセージは`missingUserIds.length === 0`の場合にすでに出し分けられているので、この修正だけで正しい表示になる。

### 2.2 【一貫性の欠如】友達機能のfetch処理にtry/catchが無い

**場所**: `src/app/(app)/friends/FriendsPanel.tsx`(`handleAdd`)、`src/app/(app)/friends/FriendsList.tsx`(`handleRemove`)、`src/app/friends/add/[code]/AddFriendButton.tsx`(`handleAdd`)

**症状**: いずれも`fetch`を`try/catch`で囲っていない。オフラインやネットワーク瞬断で`fetch`自体が例外を投げると、`setBusy(false)`が実行されずボタンが**永久にdisabledのまま固まる**上、エラーメッセージも出ない。

**比較**: 同じアプリ内の`SessionRecorder.tsx`(`handleConfirm`)や`LoginForm.tsx`/`RegisterForm.tsx`は`try { ... } catch { setError(...) } finally { setSubmitting(false) }`のパターンで正しく実装されている。友達機能だけこのパターンが抜けている(今回の開発で新規追加した箇所の考慮漏れ)。

**対応案**: 3箇所に`try/catch/finally`を追加。重複が多いので、この機会に共通の`postJson`ヘルパー(fetch→JSON parse→busy解除→エラーハンドリングを1箇所に集約)を`src/lib/api-client.ts`のような形で切り出し、6箇所以上で似たコードが重複している状態を解消することを推奨(3.3も参照)。

## 3. UX/UI改善提案(バグではないが改善余地あり)

優先度順に記載。

### 3.1 [中] デスクトップでもハンバーガーメニューのまま

`AppShell.tsx`はモバイル/デスクトップ問わず同じ「ハンバーガー+オーバーレイdrawer」パターンを使っている。1440px幅のデスクトップでも、ナビを開くたびにコンテンツが暗転してオーバーレイが被さる(`04-nav-drawer__desktop.png`参照)。デスクトップでは十分な横幅があるため、`min-width`に応じて常時表示のサイドバーに切り替えるとPC利用時の体験が良くなる(例: `@media (min-width: 900px)`でdrawerを固定サイドバー化し、ハンバーガーボタンを非表示に)。

### 3.2 [中] 友達解除の確認が素の`window.confirm()`

`FriendsList.tsx`の友達削除は`window.confirm()`を使っている。ブラウザネイティブのダイアログはOS/ブラウザによって見た目がバラバラで、アプリのデザインシステム(素のCSSで統一されたカード・ボタン)から浮く。既存の`status-banner`や`card`のスタイルを流用した確認モーダルに置き換えると統一感が出る(優先度は低めだが、他に確認ダイアログを使っている箇所が無いため、ここだけ浮いて見える)。

### 3.3 [中] fetch呼び出しの重複が多い(保守性)

`LoginForm`・`RegisterForm`・`SessionRecorder`・`FriendsPanel`・`FriendsList`・`AddFriendButton`の6箇所で、ほぼ同一の「`fetch` → `res.json()` → `!res.ok`ならエラー表示 → busy解除」という手続きが個別に書かれている。2.2の修正と合わせて共通化すると、今後同種のバグ(try/catch漏れ)が再発しにくくなる。

### 3.4 [低] 友達コード・QRの共有手段がコピーのみ

`/friends`の「コピー」ボタン以外に共有手段がない。モバイルでは`navigator.share()`(Web Share API)が使える端末が多く、LINEやメッセージアプリへワンタップで送れると、まさに今回目指した「LINEのID交換に近い」体験により近づく。対応ブラウザでのみボタンを出す(feature detection)形であれば安全に追加できる。

### 3.5 [低] ページ遷移中のローディング表示が無い

期間タブ・カレンダーの月送り・友達一覧など、多くがサーバーコンポーネントの再取得を伴うリンク遷移だが、Next.jsの`loading.tsx`が用意されていないため、低速回線では遷移中に何の反応もない空白時間が発生しうる。主要な動的ルート(`/friends`, `/me`, `/members/[userId]`, `/sessions`)に軽量な`loading.tsx`(スケルトンまたはスピナー)を追加すると体感速度が上がる。

### 3.6 [低] デスクトップの余白が大きい

`page-shell`が`max-width: 640px`で固定されているため、1440px幅のデスクトップでは左右に大きな余白ができる(意図的なモバイルファースト設計と思われるため、バグではなく提案)。将来的にホーム画面などを2カラム(統計+直近の対局を横並び)にする余地はあるが、実装コストと見合うかは要検討。今回は「そのままでも問題ない」という結論で優先度は低い。

### 3.7 [低] robots制御が無い

個人の収支という機微情報を扱うアプリだが、`<meta name="robots">`も`robots.txt`も設定されていない。ログイン必須ページ自体は検索エンジンにインデックスされても中身は見えないが、ログイン/登録ページはインデックスされ得る。`src/app/layout.tsx`の`metadata`に`robots: { index: false, follow: false }`を追加するだけで対応できる、コストの低い改善。

### 3.8 [情報] friendCodeの総当たり対策

`docs/spec-friends.md`にも記載済みだが、8桁のfriendCodeは約1.1兆通りあり実用上の推測は困難なものの、`/api/friends`にレート制限は無い。現状の利用規模(友人間の少人数アプリ)では優先度は低いと判断し今回は対応不要としたが、将来ユーザー数が増える場合は簡易的なレート制限(IPまたはユーザー単位、1分あたりのリクエスト数制限)の追加を検討する。
